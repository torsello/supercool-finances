     Findings

     1. Medium: an unknown path with a body that can't be parsed answers 500 instead of 404
     - Where: src/platform/http/routes.ts:25, together with src/platform/http/error-handler.ts:115 and :158.
     - What is wrong: Fastify sends unknown paths through the root not-found handler, but it still parses the body before that handler runs. A parse failure or an unsupported content type reaches handleError, and toProblem maps it to /problems/internal-error. routes.ts says an unknown path answers 404 "before any credential is read". That holds for credentials but not for the body.
     - How to trigger:
       - POST /no-such-path (or /v1/no-such-path) with Content-Type: application/json and the body {, which raises FST_ERR_CTP_INVALID_JSON_BODY.
       - The same path with Content-Type: application/xml and any body, which raises FST_ERR_CTP_INVALID_MEDIA_TYPE.
       - Both answer 500 and write an error log line with a stack trace.
     - Impact:
       - Anyone can produce 500s at will, which breaks the rule in ADR-0016 that every 500 is a defect and adds noise to alerting.
       - Wrong status for SYS-R31 and SYS-R32.
       - Mapping parser errors to 400 (still an open task) won't fix it: these requests would then answer 400 or 415, still not the 404 that the route check owes first.
       - test/integration/overview/app.test.ts only sends requests without a body, so the tests miss this.
     - Suggested fix:
       - Add a root onRequest hook that sends the RouteNotFound problem when request.is404 is true. It runs before body parsing.
       - Or check request.is404 first in handleError.
       - Add POST cases with a broken body and a foreign content type to the SYS-R32 test.
     - AC: SYS-R32 and SYS-R31 (proven later by SYS-AC02 and SYS-AC29), SYS-R25.

     2. Medium: bad URLs bypass the problem-details model
     - Where: src/app.ts:223. Fastify({ logger }) sets no frameworkErrors and no clientErrorHandler.
     - What is wrong: When the router can't decode a path, Fastify's built-in onBadUrl writes a plain application/json 400 itself: {"error":"Bad Request","code":"FST_ERR_BAD_URL","message":"'<path>' is not a valid url component"}. It has no requestId, it is not application/problem+json, and it echoes the path back.
     - How to trigger: GET /%zz or GET /v1/%E0%A4%A. decodeURI throws inside find-my-way, which calls onBadUrl.
     - Two related cases:
       - Once /accounts/:id exists, an id longer than 100 characters hits onMaxParamLength and gets a plain 414. SYS-R42 requires 404 /problems/not-found instead.
       - A request the HTTP parser rejects gets Fastify's default client-error body.
     - Impact: The error model of SYS-R24 is broken for unknown routes, which ADR-0016 says need explicit mapping. Clients get a second error shape.
