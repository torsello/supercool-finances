  Capability: simulated authentication and authorization.                       
  Rules:                                                                        
  - Bearer JWT, HS256 for the demo with the secret from the environment, with   
  claims sub (user id), role (customer or operator), iat, exp (at most 15       
  minutes), iss and aud checked against configuration.                          
  - Tokens are minted only by a local CLI script (npm run token -- --sub <id>   
  --role <role>); the API has no endpoint that issues tokens.                   
  - Production would use an external OpenID Connect provider with asymmetric    
  keys (RS256 or ES256) through JWKS; out of scope here and recorded in an ADR. 
    Acceptance criteria must cover at least:                                    
  - Missing, malformed, expired, not-yet-valid, wrong-signature, wrong issuer   
  or audience, alg "none", or unknown role → 401 with the same generic body,    
  giving no hint of which check failed.                                         
  - A customer on an operator-only endpoint → 403.                              
  - A customer reading an account they do not own, or using it as a source      
  → 404.                                                                        
  - The destination of a transfer may belong to another customer (spec 003      
  defines the generic destination error).                                       
  - The user id comes only from the token, never from the body or the query     
  string; a body field such as ownerId is rejected as unknown.                  
  - An authorization matrix (endpoint × role × own or foreign account) is       
  written as a table in this spec, and a single AC requires one table-driven    
  e2e test covering every cell.                                                 
    Do not write code.

  Size: 21 requirements (AUT-R01–R21) and 16 ACs: 6 unit, 9 integration, 1 e2e.

  How your rules map to ACs:
  - One generic 401 (AUT-AC02): 13 kinds of bad credentials, each sent on a read
    and on a withdrawal. All 26 answer 401 with bodies equal except requestId
    and the same WWW-Authenticate header. The health check and the API docs
    ignore the token.
  - Token checks: AUT-AC03 covers expiry, not-yet-valid and the 15-minute
    lifetime, testing both sides of each limit with an injected clock. AUT-AC04
    covers the signature and algorithm: none, HS384/512, RS256, ES256, a key
    embedded in the header, crit and a JWE. AUT-AC05 covers iss, aud, role and
    sub.
  - 403 for the wrong role: AUT-AC07 is a customer on operator-only endpoints
    and AUT-AC08 an operator on customer-only ones. The body is the same
    whatever id the path names.
  - 404 for another customer's account (AUT-AC09): reading it or using it as a
    source looks exactly like an unknown id.
  - Transfers to another customer (AUT-AC10): allowed. A destination the sender
    can't credit gets spec 003's /problems/destination-unavailable.
  - User id only from the token (AUT-AC11): ownerId/userId in the body or query
    string answers 422. X-User-Id is ignored, and a role in the body doesn't
    help.
  - Token script: AUT-AC12 checks that npm run token mints a token the API
    accepts; AUT-AC13 checks it refuses bad arguments and configuration.
  - No token endpoint (AUT-AC14): paths like /token and /login answer 404.
  - Authorization matrix: table 1.3 has 13 endpoints × 4 columns (no token,
    customer own, customer foreign, operator), 50 cells. AUT-AC16 is the single
    table-driven e2e test. It sends every cell to both replicas and fails if its
    case list and the table differ.

  Open questions (14, each with a recommended answer, all pending). The ones
  that matter most:
  - Q1: two new variables, JWT_ISSUER and JWT_AUDIENCE.
  - Q2: a fixed 5-second clock tolerance.
  - Q3: an optional nbf claim counts towards "not yet valid".
  - Q4: sub must be a UUID, used in lowercase.
  - Q5: aud may be a string or an array.
  - Q6: the exact 401 body and WWW-Authenticate: Bearer 
    realm="supercool-finances".
  - Q7: JWT_SECRET must be at least 32 bytes, so the change-me placeholder is
    refused.
  - Q8: each 401 logs a reason code, never the token.
  - Q10: nothing stops the same sub from appearing with both roles.
  - Q11: the token script has no --ttl flag.
  - Q14: a token in the query string (access_token) is not accepted.

  Conflicts with other specs:
  1. SYS-R36 (spec 000) lists only exp, sub and role as required claims. Spec
     006 also requires iat, iss, aud and the 15-minute lifetime. It doesn't
     contradict SYS-R36, but I'd reword SYS-R36 to point to AUT-R02–R05. That
     changes a requirement, so it needs your OK.
  2. 000 Q15 only defines pointer entries, which point into the request body.
     AUT-R09 rejects unknown query parameters too, so Q12 proposes a parameter
     entry for them. 000 Q15 would need extending.
  3. Follow-ups for implementation, not conflicts:
     - .env.example needs JWT_ISSUER and JWT_AUDIENCE.
     - package.json needs the token script.
     - Phase 03 needs the ADR for HS256 now and OIDC with RS256/ES256 and JWKS
       in production.

  SEC.                                                                          
  Capability: hardening and operability of the service.                         
  Acceptance criteria must cover at least:                                      
  - Rate limiting per client IP at the load balancer (nginx limit_req; AWS WAF  
  in production) and per authenticated user in the service, backed by Redis so  
  the limit is shared across replicas; exceeding either → 429 with Retry-After  
  (nginx must be configured to answer 429, not its default 503).                
  - Limits are configurable through environment variables. Defaults are sized   
  so the e2e and load suites stay under them (per IP: 500 requests per second   
  with a burst of 1000; per user: 300 requests per 10 seconds); the rate-limit  
  test exceeds them on purpose with a dedicated user.                           
  - If Redis is unavailable the service keeps serving (per-user rate limiting   
  fails open) and logs a warning; money correctness never depends on Redis.     
  - Request body above 16 KB → 413; content types other than JSON → 415.        
  - Security headers through helmet, no X-Powered-By, CORS disabled unless      
  configured.                                                                   
  - trustProxy limited to the load balancer network, so clients cannot spoof    
  X-Forwarded-For.                                                              
  - Correlation id: X-Request-Id follows the rule of spec 000 (the client's     
  value is kept only if it matches the safe pattern, otherwise a new one is     
  generated; nginx forwards its own request id when the client sends none); it  
  is echoed in the response and present in every log line.                      
  - Logs are JSON; Authorization headers, tokens, secrets and Idempotency-Key   
  values are redacted.                                                          
  - /health/live checks only the process; /health/ready checks the database and 
  applied migrations, and fails during shutdown.                                
  - Graceful shutdown on SIGTERM: stop accepting, finish in-flight requests     
  within a deadline, close the database pool and Redis, exit 0.                 
  - Timeouts ordered so the inner layer always gives up first: database         
  statement_timeout < service request timeout < load balancer timeout;          
  idle_in_transaction_session_timeout is set. Database timeouts are set on the  
  application role (ALTER ROLE ... SET), not with per-connection SET            
  statements, which would pin connections behind RDS Proxy. The per-transaction 
  lock timeouts of specs 003 and 005 are set through a small SQL function that  
  calls set_config(..., true): the value lasts only until the transaction       
  ends, so it never leaks to another request on a pooled connection, and RDS    
  Proxy does not pin on function calls (its documentation lists SET and         
  set_config statements as pinning, but not function calls).                    
  - Pool sized so that replicas × pool size stays below the database            
  max_connections. When the pool is exhausted, a request waits at most a        
  bounded acquire timeout, shorter than the request timeout, and then answers   
  503 with Retry-After instead of hanging; bursts such as the concurrency ACs   
  of specs 000 and 003 queue briefly and never get a 5xx.                       
  - Configuration comes from environment variables validated at startup;        
  invalid configuration stops the process with a clear error.                   
  - /metrics exposes Prometheus metrics: request duration histogram by route    
  and status, money movements by type and outcome, idempotent replays, lock     
  timeouts, transaction retries, pool usage. It is served on a separate         
  internal port (METRICS_PORT) that the load balancer never routes to, so it    
  needs no credentials and is not reachable from outside.

  /docs/json) and the health checks are served outside /v1 (SYS-R43), without
