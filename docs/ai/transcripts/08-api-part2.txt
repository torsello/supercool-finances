     Findings

     1. Medium: certain JSON bodies on any keyed route get a 500 instead of 400 or 422
     - Where: src/modules/idempotency/adapters/http/key-header.ts:34-37 and src/modules/idempotency/domain/fingerprint.ts:16 and :19-27.
     - What is wrong: the preValidation hook builds the fingerprint from the parsed body for every keyed route. For two kinds of valid JSON, canonicalJson throws:
       - Huge numbers: JSON.parse turns 1e400 into Infinity, and canonicalJson throws TypeError('not a JSON number').
       - Deep nesting: the function calls itself once per level, so about 3000 levels of [[[…]]] overflow the stack with a RangeError. That body is only about 6 KB, under the 16384-byte limit of SEC-R10.

       Fastify catches the throw from the hook and passes it to handleError, which answers 500 /problems/internal-error and logs it at error level.
     - How to trigger:
       - An operator sends POST /v1/accounts/{A1}/deposits with a valid key and {"amount":1e400,"currency":"EUR"}.
       - The same request without an Idempotency-Key also gets 500. The hook runs before the key check, so it never reaches the 400 of IDM-R01.
       - The same applies to POST /v1/accounts, withdrawals, transfers and reversals, for example a body of 3000 nested arrays.
     - Impact:
       - Any authenticated caller can produce 500s and error log lines at will, which adds noise to the error rate and to alerting (SYS-R24, SYS-R34).
       - It breaks the order of checks: the request should get 400 for a missing key, or the key step and then 422 validation (MOV-R08: "is not a JSON string … 422"; SYS-R27: "a request parses but its content fails validation … 422").
       - No money moves and nothing is stored.
     - Suggested fix: make the fingerprint step never throw.
       - Catch errors in preValidation. Fall back to a fingerprint that marks the body as not canonicalizable, computed from the method, the path and a fixed marker or the raw body bytes.
       - This is safe because such a body can never pass the strict body schemas, whose fields are all strings, so its outcome is never stored. A key that matches a stored row still answers 422 idempotency-key-reused, as SYS-R31 orders.
       - Also make canonicalJson iterative, or cap its depth.
       - Add unit tests for 1e400 and deep nesting, and one HTTP test: no key gives 400, and a fresh key gives 422 with nothing written.
