❯ Using the spec skill, write specs/004-reversals/spec.md with ID prefix REV.   
  Capability: reversing a completed transaction with a compensating             
  transaction.                                                                  
  Acceptance criteria must cover at least:                                      
  - Only operators can reverse; a customer gets 403 (this is an operator-only   
  endpoint, not a foreign resource, so 403 is correct here).                    
  - A reversal creates a new transaction whose entries are the exact negation   
  of the original's, linked to it; the original is never modified.              
  - A transaction can be reversed at most once, enforced by a unique            
  constraint; a second attempt → 409 already-reversed.                          
  - A reversal cannot itself be reversed → 422.                                 
  - If reversing would take a customer account below zero (the money was        
  already spent), the reversal is rejected with 422                             
  insufficient-funds-for-reversal and nothing is written. Record the            
  alternative (allowing a negative balance as debt) under open questions.       
  - Reversals are allowed on frozen accounts (operators often reverse because   
  of fraud) and rejected with 422 account-not-active when an involved account   
  is closed.                                                                    
  - A reversal requires an Idempotency-Key and a reason (3 to 500 characters)   
  stored in the audit record.                                                   
  - Reversals follow the same lock ordering as transfers, so a reversal racing  
  a transfer on the same accounts cannot deadlock or overdraw.                  
    Do not write code.

  Your bullets, as written in the spec:
  - Operators only: a customer gets 403, with the same body for any transaction
    id (REV-R03, REV-AC04).
  - Compensating transaction: the new transaction has the original's entries
    with signs flipped, on the same accounts, linked by reversedTransactionId.
    The original is never changed (REV-R01/R02, AC01–AC03).
  - At most once: a unique database constraint on that link enforces it. A
    second attempt gets 409 already-reversed, including when the constraint
    itself rejects the insert, never a 500 (R05/R06, AC06–AC08).
  - Reversing a reversal: 422 transaction-not-reversible. The problem name is my
    choice (R07, AC09, Q3).
  - Money already spent: 422 insufficient-funds-for-reversal, nothing written.
    The alternative of allowing a negative balance as debt is recorded in Q2
    (R08, AC10).
  - Frozen and closed accounts: frozen is allowed and the account stays frozen;
    closed gets 422 account-not-active (R09/R10, AC11/AC12).
  - Idempotency-Key and reason: both required. The reason must be 3–500
    characters and is stored only in the audit record (R13–R16, AC15–AC18).
  - Lock order: the same as transfers. AC22 races a reversal against a transfer,
    and exactly one of them wins with no overdraft. AC23 runs 20 reversals with
    100 transfers in both directions with no deadlock (R18–R20).

  Rules I added beyond your list:
  - Order of checks: a fixed sequence (section 1.4); a reversal that was already
    reversed gets the 409 before any status or funds check.
  - Balance limit: a reversal that would push a balance past the maximum gets
    422 balance-limit-exceeded.
  - Maximum amount: MAX_AMOUNT_MINOR doesn't limit reversals.
  - Lock timeout: 503 with Retry-After: 1.
  - Reading a reversal by id: it shows reversedTransactionId.

  Open questions: Q2 (rejection over debt) and Q7 (frozen allowed, closed
  rejected) are marked as decided by you today. The rest are pending, each with
  a recommended answer:
  - Q1: path POST /transactions/{id}/reversals.
  - Q3: reversing a reversal gets 422; a mistaken reversal is undone by a new
    deposit or transfer.
  - Q4: the reason is counted in characters (code points), with control
    characters and whitespace-only reasons rejected. These two rejections are my
    additions.
  - Q5: the reason is never returned in a response or written to logs.
  - Q6: the order of checks.
  - Q8: what the audit record of a reversal holds.
  - Q9: the original transaction doesn't link to its reversal in this version.
  - Q10: no time limit and no second-operator approval.
  - Q11: whether a 409 is stored for replay is left to spec 005. Spec 005 also
    has to handle the case where the unique constraint aborts the transaction,
    which removes the idempotency record with it.

  Conflicts with other specs (I didn't edit them):
  - Spec 003: its transaction view (section 1.3) and MOV-R26/R27 don't mention
    reversedTransactionId. REV-R23 adds it for reversals, so 003 needs a
    matching line. That changes its requirements, so I need your approval.
  - Spec 001, Q7: it says the same thing as your rule and could be marked as
    decided by you.
  - Spec 000: its error catalogue says the capability spec decides whether a 409
    is stored for replay; this spec hands that to spec 005 (Q11).
  - Spec 002, LED-R28: ledger database rejections answer 500. The reversal
    unique constraint answers 409 instead. That's consistent, because the
    constraint belongs to this spec, but worth knowing.

  Capability: safe retries of every money-moving request across replicas.       
  Design (already decided; an ADR will record it): the key row is inserted      
  inside the same database transaction as the movement, as its first write.     
  Acceptance criteria must cover at least:                                      
  - Idempotency-Key is required on POST deposits, withdrawals, transfers and    
  reversals (missing → 400) and optional on account creation; it must be 1 to   
  255 visible ASCII characters (otherwise 400).                                 
  - Keys are scoped per authenticated user: two users may use the same key      
  independently.                                                                
  - The request fingerprint is SHA-256 over method, path and canonical JSON     
  body (sorted keys).                                                           
  - Same key and same fingerprint after completion → the stored status code and 
  body are returned unchanged, with header Idempotent-Replayed: true, and       
  nothing new is written.                                                       
  - Same key with a different fingerprint → 422 idempotency-key-reused.         
  - A replay is answered before any validation that depends on configuration: a 
  key that matches a completed request with the same fingerprint gets its       
  stored response even if MAX_AMOUNT_MINOR or another setting changed in        
  between, or another replica runs a different version.                         
  - Same key sent concurrently to two replicas → exactly one execution; the     
  other request waits for the first to finish and then receives the stored      
  response.                                                                     
  - If that wait exceeds the configured idempotency wait timeout (separate from 
  the account lock timeout of spec 003) → 409 request-in-progress with          
  Retry-After. Both waits are bounded with lock_timeout: the transaction sets   
  it to the idempotency wait timeout before inserting the key and to the        
  account lock timeout before locking the accounts, and SQLSTATE 55P03 maps to  
  409 at the key step and to 503 at the lock step.                              
  - The movement runs inside a savepoint taken after the key insert: a business 
  rejection rolls back to the savepoint, stores the rejection in the key row    
  and commits, so the key is never left without a result.                       
  - Business rejections (for example insufficient funds) are stored: a retry    
  returns the same rejection even if funds arrived in between.                  
  - Unexpected errors (5xx) store nothing: the whole transaction rolls back,    
  and a retry executes again.                                                   
  - A crash after commit but before the response is sent: the retry returns the 
  stored result, and nothing is duplicated.                                     
  - Keys expire after a configurable TTL (default 24 h); a cleanup job deletes  
  expired keys, which can then be reused.                                       
    Do not write code.

  Draft, and added it to the index in specs/README.md. It has 23 requirements
  and 25 acceptance criteria, and no code. Prettier passes, and npm run trace

  Your bullets, as written in the spec:
  - Key required, and its format:
    - Required on deposits, withdrawals, transfers and reversals; a missing key
      gets 400 (R01).
    - Optional on account creation (R02).
    - 1–255 characters from ! to ~ only (visible ASCII, no space), otherwise 400
      (R03).
  - Scope: keys are per user, so two users can use the same key (R04, AC05).
  - Fingerprint: SHA-256 over method, path and canonical JSON with sorted keys
    (R05, AC06).
  - Replay: returns the stored status and body unchanged, with
    Idempotent-Replayed: true, and writes nothing (R07, AC07). It works the same
    after a setting such as MAX_AMOUNT_MINOR changes, after the account
    changes, and on a replica running another version (R08, AC08).
  - Different fingerprint: 422 idempotency-key-reused (R09, AC09).
  - Concurrent requests with the same key: exactly one runs. A request waiting
    on another replica then gets the stored response, gets 422 if its body
    differs, or runs itself if the first one rolled back (R10, AC10–AC12).
  - Wait limits: the wait for the key gets 409 request-in-progress with
    Retry-After: 1 if it times out. The account lock has its own timeout. Error
    55P03 maps to 409 at the key step and 503 at the lock step (R11–R13,
    AC13/AC14).
  - Savepoint: a business rejection rolls back to the savepoint, is stored and
    commits (R14, AC15–AC17).
    - This also settles spec 004's Q11: the unique-constraint 409 is stored and
      replayed.
  - Not stored: validation errors (R16, AC18), and 500/503 errors, so a retry
    runs again (R17, AC19).
  - Crash after commit: the retry gets the stored result and nothing is
    duplicated (R19, AC21).
  - Expiry: keys expire after a TTL, default 24 h (R20–R22, AC22–AC24). The
    cleanup runs as npm run idempotency:cleanup.

  Rules I added beyond your list (each linked to an open question):
  - A key header sent twice gets 400 (Q5).
  - The stored response includes Content-Type and Location, not just status and
    body (Q2).
  - The database rejects any key row committed without a stored response (Q10).
  - An expired key can be reused at its TTL, even before the cleanup has deleted
    it (Q8).
  - Ranges for the two new settings: wait 1–60000 ms, TTL 1 s to 30 days (Q6).

  Open questions (all pending, each with a recommended answer):
  - Q1: a 404 for the account or transaction in the path is stored. This answers
    spec 000's Q7.
  - Q2: which response headers are stored.
  - Q3: exact fingerprint encoding. I recommend RFC 8785 for the canonical JSON,
    with the path not normalised, so the same id in different letter case
    counts as a different request.
  - Q4: keys are case-sensitive and shared across all endpoints for a user.
  - Q5: a duplicated key header gets 400.
  - Q6: setting names, defaults and ranges.
  - Q7: Retry-After: 1 on the 409.
  - Q8: expiry happens at the TTL, not only when the cleanup runs.
  - Q9: how the cleanup runs: a command that deletes in batches and skips rows
    in use, scheduled hourly once the infrastructure exists.
  - Q10: the database enforcement above.
  - Q11: the TTL counts from when the key row is created.
  - Q12: a retry after expiry runs again and can move money twice. I recommend
    accepting and documenting this.
