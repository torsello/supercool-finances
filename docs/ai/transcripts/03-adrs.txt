❯ Using the adr skill, record these accepted decisions, one ADR each, in this   
  order, with status Accepted. Keep my reasoning; add technical detail, the     
  alternatives with honest pros and cons, and consequences, and link each ADR   
  to the spec requirements it explains. Where a spec already fixed a detail,    
  the ADR follows the spec.                                                     
                                                                                
  0001 Spec-driven development with ADRs and AI agents. Behaviour is defined in 
  specs with acceptance criteria before code; decisions are recorded as ADRs;   
  AI agents follow AGENTS.md; an independent review (/audit) runs before every  
  push. Every AC is proven by a test that actually ran and passed: npm run      
  trace reads Vitest's JSON reports, not the test source, and enforces coverage 
  for every ticked task in tasks.md, so the gate works from the first           
  implementation phase. Alternative: code first with docs at the end, which     
  starts faster but lets behaviour and rationale drift and makes AI output      
  harder to verify.                                                             
                                                                                
  0002 Modular monolith. One bounded context (balances) where a transfer must   
  update two accounts atomically. One deployable with internal modules          
  (accounts, ledger, movements, idempotency, auth, http, platform) gives ACID   
  transactions without sagas or distributed transactions, and still scales      
  horizontally as stateless replicas. Microservices give independent deploys    
  and scaling, but would split one consistency boundary and add network failure 
  modes for no benefit at this size. Modules have explicit interfaces, so one   
  could be extracted later.                                                     
                                                                                
  0003 Hexagonal architecture with tactical DDD inside each module. Each module 
  has a domain layer (value objects such as Money and Currency, aggregates      
  such as Account and LedgerTransaction that enforce their own invariants,      
  typed domain errors) that imports no framework or database code; an           
  application layer with the use cases and the ports they need; and adapters    
  for HTTP (Fastify) and persistence (Kysely). Business rules are unit-tested   
  without a database or HTTP server, and a lint rule keeps the domain free of   
  infrastructure imports. The unit of work and row locking are explicit ports,  
  not hidden behind a generic CRUD repository, because the money guarantees     
  depend on them; the database still enforces the invariants as a second line   
  of defence. Reads such as account history go through simple query services    
  that bypass the aggregates. MVC was considered: it fits user interfaces, but  
  in an API it tends to put business rules in controllers or ORM models, mixed  
  with HTTP and persistence. Full DDD with event sourcing and CQRS was          
  considered too: strong for auditing, but the double-entry ledger already      
  gives an immutable history at a fraction of the complexity.                   
                                                                                
  0004 TypeScript with Fastify. Fastify gives schema-based validation and       
  serialization, encapsulated plugins, good performance and first-class         
  TypeScript. Express lacks built-in validation and async error handling;       
  NestJS adds a heavy decorator-based framework that hides control flow we want 
  explicit.                                                                     
                                                                                
  0005 PostgreSQL as the only source of truth. The challenge allows in-memory   
  storage, but several replicas behind a load balancer and crash safety require 
  shared, durable state. PostgreSQL gives ACID transactions, row locks, check   
  constraints, unique indexes and deferrable constraint triggers, so the        
  database itself enforces the invariants. Redis holds only rate-limit          
  counters, so money correctness never depends on it. SQLite has a single       
  writer and no network access; in-memory state is lost on restart and not      
  shared between replicas.                                                      
                                                                                
  0006 Double-entry ledger with signed integer minor units. Every movement is a 
  balanced set of immutable entries, one signed amount per entry, which makes   
  money auditable and the invariants checkable with SQL. Amounts are bigint     
  minor units with a per-currency exponent; floats are never used. Corrections  
  are compensating reversals, never edits. Alternative: a single mutable        
  balance column, simpler but with no audit trail and no way to prove           
  correctness.                                                                  
                                                                                
  0007 System accounts without a cached balance, never locked. Every deposit    
  and withdrawal touches a settlement account; locking or updating its row      
  would serialize all of them. Their balance is derived from entries instead,   
  with arbitrary precision so it never overflows. The lock query selects only   
  customer accounts, so a system account named as a transfer destination is     
  never locked either. The shared FOR KEY SHARE that the foreign key check      
  takes on the settlement row is accepted, because it never blocks another      
  movement; its cost is measured in the load test. Customer accounts keep a     
  cached balance with CHECK (balance >= 0) for fast reads and a database-level  
  guarantee, verified by reconciliation.                                        
                                                                                
  0008 Concurrency control with READ COMMITTED and ordered pessimistic row      
  locks. Lock the involved customer accounts with SELECT ... FOR UPDATE one by  
  one in ascending uuid order, validate after locking, never lock system        
  accounts, and retry the whole transaction on deadlock or serialization errors 
  at most 3 times as a safety net. Each lock wait is bounded by a               
  per-transaction lock timeout and answers 503 with Retry-After. SERIALIZABLE   
  is also correct, but under contention on hot accounts it aborts and retries   
  many transactions; optimistic locking with a version column has the same      
  retry problem.

❯ Using the adr skill, record these accepted decisions, one ADR each,           
  continuing the numbering, with status Accepted. Keep my reasoning; add

  0009 Idempotency inside the movement's transaction. The key row is the first  
  write of the same transaction, so the key and its effect commit or roll back  
  together: no stuck "in progress" keys and no recovery job. Concurrent         
  duplicates wait on the key row and then read the stored response; the wait is 
  bounded and holds a pool connection, which is the main cost. A savepoint      
  after the key insert lets a business rejection be stored and committed        
  without its effects. A replay is answered before validation, so a             
  configuration change or a newer version never turns an applied movement into  
  an error. Keys expire after 24 hours and an hourly job deletes them.          
  Alternatives: a two-phase design (claim the key, commit, execute, complete)   
  is needed when calling external systems that cannot join the transaction; we  
  have none, so it is the documented evolution path. A Redis store would make   
  money correctness depend on Redis (SEC-R07) and cannot commit atomically with 
  the ledger. A stored status with client polling adds a state machine and      
  recovery for keys left in progress. In-process memory is not shared between   
  replicas.                                                                     
                                                                                
  0010 Kysely and pg instead of an ORM. Money code needs explicit transactions  
  and row locks. Kysely is a typed SQL builder with forUpdate() and no hidden   
  queries; migrations are plain SQL, so constraints and triggers are            
  reviewable. Prisma and TypeORM hide transaction and locking semantics; raw pg 
  alone loses type safety.                                                      
                                                                                
  0011 Amounts as strings in the API and bigint in the domain. JSON numbers     
  lose precision above 2^53 in JavaScript clients, and pg already returns       
  bigint as a string. Digit strings in minor units are unambiguous, validated   
  by a strict regular expression and a bigint range check, and converted to     
  bigint at the edge. Alternative: decimal strings ("10.50"), friendlier to     
  read but they mix formatting with value and depend on the currency exponent.  
                                                                                
  0012 Simulated authentication with JWT and two roles. The challenge allows    
  simulating authentication. HS256 tokens, with the algorithm pinned, a secret  
  of at least 32 bytes, sub, role, iss, aud and a 15-minute exp, minted by a    
  CLI script; the API never issues tokens, and every failure answers the same   
  401. Roles: customer and operator, one per identity. Production: an external  
  OIDC provider with asymmetric keys (RS256 or ES256) and JWKS rotation, and    
  mTLS between internal services. The service keeps UUID user ids (AUT-R03), so 
  a provider whose subjects are not UUIDs needs a mapping: a users table from   
  (issuer, subject) to a UUIDv7 created the first time the subject is seen. A   
  UUIDv5 derived from issuer and subject was considered: stateless, but it ties 
  every id to one provider forever.                                             
                                                                                
  0013 Rate limiting at the edge and in Redis. In-memory limits break with      
  several replicas. nginx (AWS WAF in production, with a one-minute window)     
  limits per IP before traffic reaches the service; the service limits per user 
  with a fixed window in Redis, shared by all replicas, and fails open if       
  Redis is down because money correctness never depends on it. A                
  PostgreSQL-backed limiter would add write load to the critical database.      
                                                                                
  0014 AWS deployment on ECS Fargate with RDS PostgreSQL. Long-lived stateless  
  containers fit connection pooling and graceful shutdown; Fargate removes      
  server management; RDS Multi-AZ gives managed failover and backups, and RDS   
  Proxy absorbs connection spikes during scaling and failover. Private tasks    
  reach AWS services through VPC endpoints instead of a NAT gateway. Containers 
  report liveness, the load balancer checks readiness, so a database outage     
  never makes ECS replace every task. Lambda brings cold starts and connection  
  storms; EKS adds operational overhead not justified for one service; Aurora   
  PostgreSQL fails over faster but costs more, so it is the upgrade path.       
                                                                                
  0015 Terraform for infrastructure as code. Widely known, with a plan and      
  review workflow, reusable modules, and static scanning with tflint and        
  checkov in CI through npm run infra:validate, which runs pinned Docker        
  images. Secrets are created without values, so none enters the state. AWS CDK 
  and Pulumi would let us use TypeScript, but Terraform is easier for most      
  reviewers to read. The code is validated and scanned in CI, never applied     
  from this repository.                                                         
                                                                                
  0016 Error model. Every error is RFC 9457 problem details with a requestId.   
  400 means the request itself is malformed (JSON that does not parse, a        
  missing or malformed required header, an invalid cursor); 422 means it was    
  understood and refused (validation errors with one entry per field, and money 
  movements refused by a business rule); 409 means it conflicts with the        
  current state of the resource it acts on (status changes, an already reversed 
  transaction, an idempotency key still in progress). A single 400 for          
  everything is simpler, but clients could not tell a bug in their request from 
  a business refusal.                                                           
                                                                                
  0017 Keyset pagination with signed cursors. Lists page by (created_at, id),   
  never by offset; an entry's created_at is taken after its account lock is     
  held, so entries of one account are ordered as they committed and a history   
  page never skips or repeats one. The cursor is opaque, carries created_at at  
  microsecond precision and the user it was issued to, and is signed with       
  HMAC-SHA256 using CURSOR_SECRET, a secret separate from JWT_SECRET and shared 
  by all replicas, so a tampered or foreign cursor answers 400 on any replica.  
  Offset pagination is simpler but slow on deep pages and unstable while        
  entries arrive.                                                               
                                                                                
  0018 Two database roles. An owner role runs the migrations and owns the       
  tables; the service connects with a runtime role that holds only the          
  privileges it needs (SELECT and INSERT on the ledger), so a bug or a          
  compromised service cannot disable the database checks. Triggers reject       
  UPDATE, DELETE and TRUNCATE on the ledger even for the owner; only DDL or a   
  superuser could bypass them, and the service never connects as either. One    
  shared role is simpler but lets the application turn off its own safety net.  
                                                                                
  0019 Timeout layers and RDS Proxy. Each layer gives up before the layer       
  outside it (lock waits < statement timeout < request timeout < load           
  balancer), and the service refuses to start with a configuration that breaks  
  that budget. Database timeouts are set on the runtime role; the               
  per-transaction lock timeouts go through a small SQL function that calls      
  set_config(..., true), so they last only until the transaction ends and RDS   
  Proxy does not pin the connection. Source: the AWS page "Avoiding pinning an  
  RDS Proxy" (https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/rds-proxy- 
  pinning.html) lists SET and set_config among the PostgreSQL pinning           
  conditions, and says that calling stored procedures and stored functions      
  doesn't cause pinning, because RDS Proxy doesn't detect session state changes 
  made inside them; the setting is transaction-local, so no state survives the  
  transaction. Follow-up in phase 12-infra: re-check the page and alarm on      
  DatabaseConnectionsCurrentlySessionPinned. Per-connection SET statements are  
  simpler but pin connections behind RDS Proxy.                                 
                                                                                
  0020 Expand-then-contract migrations. Migrations run as a separate one-off    
  task before the new version rolls out, and every change is backwards          
  compatible with the running version; readiness accepts migrations newer than  
  the code. Running migrations at service startup is simpler but races between  
  replicas and couples deploys to schema changes.

     1. Medium: the ADRs never say which body the idempotency fingerprint is computed from
     - Where: docs/adr/0004-typescript-with-fastify.md:62-64, together with docs/adr/0011-amounts-as-strings-in-the-api-and-bigint-in-the-domain.md:28
     - What is wrong: ADR-0004 registers every route with attachValidation and says "The handler never uses the body before that check". But spec 005 §1.1 step 2 computes the fingerprint from the body before validation (step 5), so that sentence contradicts the spec. The design also leaves open which body gets hashed. When a body passes validation, Fastify replaces request.body with the Zod output before the handler runs. ADR-0011 says amounts become bigint "once, at the HTTP edge", which in practice means a Zod transform.
     - How to trigger it: In phase 08, use an amount schema with .transform(BigInt) and compute the fingerprint in the handler. JSON canonicalization cannot serialize a bigint, so every valid keyed movement fails with a 500. A second case: if destinationAccountId is lowercased by a transform (MOV-R30), C1 can send a transfer with key k1 and an uppercase destination, then the same transfer with k1 and a lowercase destination. The second request gets the first one's stored 201 back instead of 422 idempotency-key-reused.
     - Impact: Either every valid keyed movement fails, or two different bodies share one fingerprint and the second is answered with the first one's stored response.
