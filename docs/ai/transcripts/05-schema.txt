  ⎿  Findings

     1. Medium: the production pool has no 'error' listener, so one dropped idle connection crashes the process

     - Where: src/platform/db/database.ts:23
     - What is wrong: createPool returns a pg.Pool with no pool.on('error', …). When a connection sitting idle in the pool loses its backend, pg-pool emits 'error' on the pool. With no listener, Node treats it as an unhandled 'error' event and exits.
     - How to trigger: open a pool with createPool, run one query so a client sits idle, then run SELECT pg_terminate_backend(<that pid>) as a superuser. A Postgres restart or an RDS failover does the same.
     - Impact: once 08-api wires this pool into the app, a database restart or failover kills every replica at once and drops all in-flight requests. It is not reachable yet, because only tests use it. No plan or task adds this listener: plan 007 covers pool size, the acquire timeout and shutdown only.
     - Suggested fix: in createPool, attach a listener that logs the error at warn with the SQLSTATE and no connection string. Add an integration test that terminates an idle pool backend and checks the process survives and the next query succeeds.
     - AC: missing AC (failure handling, SEC-R27/SEC-R28 area).

     2. Low: numeric[] values come back as JavaScript floats, despite the "exact strings" promise

     - Where: src/platform/db/database.ts:12
     - What is wrong: exactTypes() overrides only the scalar INT8 and NUMERIC parsers. pg-types still parses _numeric (OID 1231) with parseFloatArray (node_modules/pg-types/lib/textParsers.js:189). The comment says numeric always stays an exact string, which is not true for arrays.
     - How to trigger: SELECT ARRAY[9223372036854775807::numeric * 2] returns [18446744073709552000] instead of "18446744073709551614". So would array_agg over a SUM(amount).
     - Impact: silent loss of precision on money for any future query that returns numeric arrays, such as per-currency totals. No current or planned query does this, so it is latent.
     - Suggested fix: also register OID 1231 with a parser that keeps elements as strings. Extend test/integration/platform/database.test.ts with a numeric[] and an int8[] case.
     - AC: LED-R27.

     3. Low: the database lets a later transaction append entries to an already committed ledger transaction

     - Where: migrations/1791468170000_ledger.sql:76
     - What is wrong: the deferred check fires only for the entries just inserted. It checks the whole transaction's count, sum and currency, but not whether that transaction row was written by the current database transaction.
     - How to trigger: as scf_app, take a committed deposit T1 and insert +100 on A2 and −100 on S with transaction_id = T1, then raise A2's balance by 100 and commit. Every check passes.
     - Impact:
       - A committed transaction's contents change after the fact, which goes against SYS-R15 and the "one transaction per movement" rule of LED-R01.
       - A later reversal of T1 would also negate the appended entries.
       - The money shows up in history under T1's id, with no audit record of its own.
       - ADR-0018 says a defect or injection in the service cannot corrupt the ledger; this path gets around that.
     - Suggested fix: either add a BEFORE INSERT check on ledger_entries that refuses an entry whose transaction row was not inserted by the current database transaction (or any of its savepoints), with a test, or record this gap as accepted in spec 002 section 1.3.
     - AC: missing AC (SYS-R15, LED-R01).

     4. Low: the Kysely Database types contradict plan 001 section 5 and the append-only tables

     - Where: src/platform/db/schema.ts:21, :36, :45, :55, :71
     - What is wrong:
       - Every created_at and updated_at is typed as Date. pg's default timestamptz parser does return a Date, which keeps only milliseconds. Plan 001 section 5 says these values are always read as microsecond RFC 3339 strings, never through a Date.
       - TransactionsTable, LedgerEntriesTable and AuditRecordsTable declare columns that can be updated, although the database refuses any update.
     - How to trigger: in 06-domain, write selectFrom('ledger_entries').select('created_at') and build a cursor from the result. Two entries in the same millisecond then compare equal, and keyset pages can skip or repeat an entry.
     - Impact: the types steer the next phase toward losing the precision that ACC-R22 and LED-R18 depend on.
     - Suggested fix: for timestamp columns, make the select type never (forcing the to_char expression) or a branded string. Make every column of the three append-only tables ColumnType<…, …, never> for updates.
     - AC: ACC-R22, LED-R18 (plan 001 section 5).

     5. Low: the LED-AC05 test accepts any integrity error, not the one each case should raise

     - Where: test/integration/ledger/database-checks.test.ts:163
     - What is wrong: expect(refusal.error.code).toMatch(/^23/) passes for any class-23 error, including 23502 (not null) or 23514 (check). It also never checks whether the write was refused at the insert or at commit.
     - How to trigger: drop ledger_entries_account_id_currency_fkey but keep a check that fails for some other reason. The test still passes.
     - Impact: the test proves less than LED-AC05 claims. All four cases should fail at the insert with 23503, on ledger_entries_transaction_id_currency_fkey or ledger_entries_account_id_currency_fkey.
     - Suggested fix: assert { at: 'insert', error: { code: '23503', constraint: … } } for each case, as ledger-schema.test.ts already does.
     - AC: LED-AC05.

     6. Low: docs no longer match the code

       - Spec 002 section 1.3 still says phase 05-schema "replaces the single role scf that docker/postgres/init creates today". That role is now gone.
