❯ Using the spec skill, write specs/002-ledger/spec.md with ID prefix LED.      
  Capability: the double-entry ledger that records every money movement.        
  Acceptance criteria must cover at least:                                      
  - Every transaction has two or more entries with signed amounts in minor      
  units (positive credits the account, negative debits it); no entry has        
  amount 0.                                                                     
  - The entries of a transaction sum to zero per currency; the database rejects 
  the commit otherwise. The check runs at commit time, because entries are      
  inserted one by one.                                                          
  - All entries of a transaction share one currency (no FX).                    
  - Each supported currency has one system settlement account (for example      
  external-settlement:USD), the counterparty of deposits and withdrawals; it    
  may go negative.                                                              
  - Customer accounts keep a cached balance, updated in the same database       
  transaction as their entries, that can never go below zero; a database        
  constraint enforces it, not only the code.                                    
  - System accounts keep no cached balance; their balance is the sum of their   
  entries. They are never row-locked, so they cannot become a contention point. 
  - Ledger entries are immutable: the database rejects UPDATE and DELETE on     
  them.                                                                         
  - Reconciliation: a query and an npm script (npm run reconcile) report every  
  customer account whose cached balance differs from the sum of its entries,    
  plus the global sum per currency; after any test run they report zero         
  discrepancies and a global sum of zero.                                       
  - Amounts are bigint minor units. The maximum single amount is configurable,  
  default "100000000000". An operation that would overflow a balance is         
  rejected with 422 and writes nothing.                                         
    Do not write code.

⏺ I wrote specs/002-ledger/spec.md (status Draft, prefix LED) and added it to
  the index in specs/README.md. It has 28 requirements (LED-R01 to R28) and 23 
  acceptance criteria: 4 unit, 18 integration and 1 ci. Prettier passes and npm 
  run trace exits 0, with every LED AC pending except LED-AC17. No code was
  written.

  What it covers, beyond your list:
  - Entry times: an entry's createdAt comes from the clock when it is inserted,
    after the account lock is held. Spec 001 Q14 deferred this decision to the
    ledger spec.
  - Database role: the service connects with a role that does not own the ledger
    tables, so it cannot switch off the database checks (LED-R17).
  - Locks: a test holds a lock on the EUR settlement account's row. 100
    movements must all finish while it holds that lock, and the row must be
    unchanged afterwards (LED-AC09).
  - No overflow on system accounts: their balances and the reconciliation sums
    are computed exactly, even below the 64-bit minimum (LED-R15).
  - Database rejections: if the database refuses a ledger write, the service
    answers 500 and writes nothing, because the domain checks the same rules
    first (LED-R28).

  Open questions (each has a recommended answer):
  1. Settlement account identity: a normal account id, plus a unique code such
     as external-settlement:USD.
  2. Maximum amount: the setting is MAX_AMOUNT_MINOR, one value for all
     currencies. It applies to deposits, withdrawals and transfers, but not to
     reversals.
  3. Amount above the maximum: 422 /problems/validation-error, checked before
     the account lookup.
  4. Balance overflow: 422 /problems/balance-limit-exceeded.
  5. Database roles: a separate owner role and runtime role. Today
     docker/postgres/init creates one role, scf, that owns both databases, so
     phase 05 has to change it.
  6. npm run reconcile: one read-only snapshot, JSON output, exit codes 0, 1
     or 2.
  7. "Zero discrepancies after any test run": tests share the test database. A
     test that needs a mismatch makes it inside a transaction it rolls back, or
     in a throwaway database.
  8. Global sum: customer cached balances plus system account entries, matching
     SYS-AC11.
  9. Check at commit: done with a deferred trigger.
  10. Foreign key lock: inserting an entry briefly takes a shared lock on the
      settlement account's row. It never blocks another movement; I recommend
      keeping the foreign key and measuring the cost in the load test.

  Conflicts and caveats:
  - "Writes nothing" on overflow: LED-R26 guarantees no transaction, entry,
    balance change or audit record. Whether the 422 itself is saved for
    idempotent replay is left to spec 005 (000 Q7), so an idempotency row could
    still be written.
  - Spec 000 still says "set by spec 002": SYS-R40 and its error table don't
    name /problems/balance-limit-exceeded yet. Updating them is a requirement
    change, so I didn't touch spec 000.
  - LED-AC17 is not really proven yet: npm run trace marks it covered because it
    has a Verified by line, but the CI step that runs npm run reconcile after
    the integration tests doesn't exist. Neither does the reconcile script; both
    need to be added in phase 05.
  - Not checked by npm run trace: ACs that use spec 003 or 005 behaviour
    (transfers, problem types, replay) assume those specs agree once they are
    written.

  MOV.                                                                          
  Capability: deposits, withdrawals and transfers.                              
  Rules:                                                                        
  - Deposit: operator only (it simulates money arriving from a payment rail).   
  Credits a customer account and debits that currency's settlement account.     
  - Withdrawal: the account owner. Debits the customer account and credits the  
  settlement account.                                                           
  - Transfer: the owner of the source account, to any active account in the     
  same currency.                                                                
  - Every operation is one database transaction and requires an Idempotency-Key 
  (behaviour defined in spec 005).                                              
    Acceptance criteria must cover at least:                                    
  - Happy path of each operation, with the resulting balances and ledger        
  entries.                                                                      
  - Amount validation, each rejected with 422 and field-level details: "0",     
  negative, non-numeric, decimals ("10.50"), leading zeros, above the           
  configured maximum, missing.                                                  
  - Request currency different from the account currency → 422; transfer        
  between accounts of different currencies → 422.                               
  - Transfer to the same account → 422.                                         
  - Source account frozen or closed → 422 account-not-active.                   
  - Destination missing, belonging to another customer and frozen or closed, a  
  system account, or one whose balance would overflow → 422                     
  destination-unavailable, with exactly the same response in every case, so a   
  customer cannot enumerate accounts or learn anything about another customer's 
  account.                                                                      
  - Insufficient funds → 422 insufficient-funds; nothing is written and         
  balances are unchanged.                                                       
  - An account lock that cannot be acquired within the configured account lock  
  timeout → 503 with Retry-After; nothing is written and a retry with the same  
  Idempotency-Key is safe.                                                      
  - Reading a transaction by id (GET): allowed for an operator and for the      
  owner of any customer account involved; anyone else gets 404.                 
  - Concurrency: 100 concurrent withdrawals on one account whose balance covers 
  only some of them → the accepted ones sum to at most the balance, the rest    
  fail with insufficient-funds, and the balance never goes below zero.          
  - Concurrency: crossed transfers A→B and B→A in parallel complete without     
  deadlock errors reaching the client.                                          
  - Each movement writes an audit record (actor, action, accounts, transaction, 
  correlation id) in the same transaction.                                      
  - The response returns transaction id, type, amount, currency, created_at and 
  the resulting balance of the caller's own account only.                       
    Do not write code.

     - Where: specs/003-money-movements/spec.md:285 (Q7), together with MOV-R06 at line 67 and MOV-R19/R20 at lines 80-81.
     - What is wrong:
       - Q7 applies SET LOCAL lock_timeout to the whole movement transaction.
       - MOV-R06 makes the idempotency insert the first write of that transaction.
       - When a second request with the same key arrives while the first is still in progress, its insert waits on the first transaction's lock. PostgreSQL's lock_timeout covers that wait too, so it ends with 55P03 after ACCOUNT_LOCK_TIMEOUT_MS.
       - Per MOV-R20 and Q7, 55P03 maps to 503. But spec 000 (line 359, SYS-R34) says a key still in progress after the idempotency wait timeout answers 409, under its own setting.
     - How to trigger: two identical withdrawals with Idempotency-Key k1, where the first is held on A1's row lock for longer than ACCOUNT_LOCK_TIMEOUT_MS. The second gets 503 service-unavailable instead of 409 after the idempotency wait timeout.
     - Impact: the two timeouts can't be configured separately, a client sees the wrong status and retry semantics, and spec 005 can't be implemented as spec 000 describes.
     - Fix: in 003, require SET LOCAL lock_timeout = ACCOUNT_LOCK_TIMEOUT_MS to be issued only after the idempotency record is written, immediately before the first account FOR UPDATE. The key insert would then run under the idempotency wait timeout. Also require that a 55P03 on the key insert is never mapped to 503, and add an AC in which both timeouts expire with different values.
     - AC: MOV-R19, MOV-R20, SYS-R34 (missing AC)

     Findings

     1. Medium (idempotency): a replay can get a validation 422 instead of its stored answer
     - Where: specs/000-overview/spec.md:111 (SYS-R31) against :113 (SYS-R33); specs/002-ledger/spec.md:62 (LED-R24); specs/003-money-movements/spec.md:47-50.
     - What is wrong: SYS-R31 answers the first failing check: malformed (400), then validation (422), then lookup (404). LED-R24 puts the MAX_AMOUNT_MINOR check "at the validation step of SYS-R31". MOV section 1.4 writes the idempotency record only after steps 1 to 3. Nothing says the replay lookup comes before validation, but validation depends on configuration that can change.
     - How to trigger it:
       - A withdrawal of "500" with key k1 commits (201).
       - MAX_AMOUNT_MINOR is lowered to "100", or a rolling deploy leaves replicas with different values or schemas.
       - The client retries with k1. Read literally, SYS-R31 answers 422 /problems/validation-error, not the stored 201.
     - Impact: the client is told a movement that was applied failed. If it resubmits with a new key, the money moves twice. That breaks spec 000's "never duplicated" goal.
     - Suggested fix: state in SYS-R31 and SYS-R33 that the replay lookup (key plus fingerprint of the parsed body) runs right after the 400 step, before any validation that depends on configuration. Add an AC that lowers MAX_AMOUNT_MINOR between the first request and its replay. The full semantics can still live in spec 005.
     - AC: SYS-R33 / missing AC.

     2. Medium (tests, idempotency and concurrency): MOV-AC19 depends on a fixed 100 ms gap
     - Where: specs/003-money-movements/spec.md:246.
     - What is wrong: R2 is sent "100 ms later" and must find R1's uncommitted key row already there.
     - How to trigger it: on a slow or cold CI runner (first pool connection, JIT), R1 hasn't inserted its key within 100 ms. R2 then becomes the first request: it waits on A1's lock and gets 503, while R1 waits on the key and gets 409. The AC's assertions fail.
     - Impact: a flaky test on the exact behaviour that separates the two timeouts. A red run looks like a real regression.
     - Suggested fix: send R2 only once R1 is seen waiting on A1's row lock (poll pg_locks / pg_stat_activity for R1's backend), not after a fixed delay. Assert the order by events, not by wall-clock offsets.
     - AC: MOV-AC19.

     3. Medium (tests, traceability gate): a ci AC is "covered" by any text that names no npm run script
     - Where: scripts/traceability.ts:482 (with ciGapsOf at :412); test/fixtures/traceability/passing/specs/001-alpha/spec.md:15.
     - What is wrong: a ci AC counts as proven when its Verified by text has no gaps, and text naming no npm run script never has any. Steps that cannot fail (|| true, continue-on-error: true, if: false) also count as proof.
     - How to trigger it:
       - The fixture's ZZA-AC02, Verified by: CI job terraform (terraform validate), is reported covered, although the fixture's ci.yml has no terraform job.
       - - run: npm run reconcile || true would make LED-AC17 covered even though reconcile could never fail the build.
     - Impact: the Terraform ACs of phase 12, and LED-AC17, can pass the gate with nothing behind them.
     - Suggested fix: require every ci line to name at least one concrete command that appears in a CI step. Reject steps with continue-on-error, if: false or a trailing || true. Change ZZA-AC02 so the fixture actually has that step.
     - AC: missing AC (gate behaviour, specs/README).

     4. Low (failure handling): the timeout ordering compares single timeouts, not the total wait
     - Where: specs/000-overview/spec.md:115 (SYS-R35); specs/003-money-movements/spec.md:80 (MOV-R19).
     - What is wrong: MOV-R19 applies lock_timeout to each row, so a transfer can wait twice. SYS-R18 allows 3 attempts. The idempotency wait comes on top.
     - How to trigger it: with the default ACCOUNT_LOCK_TIMEOUT_MS of 2000, the database wait can reach about 3 × (idempotency wait + 2 × 2000 ms) plus backoff. That passes "each database timeout < request timeout" and still exceeds the request timeout.
     - Impact: the load balancer cuts requests off, which is exactly what SYS-R35 is meant to prevent.
     - Suggested fix: word SYS-R35 as a worst-case budget per request (sum over attempts and locks), so spec 007 sets values against that sum.
     - AC: SYS-R35.

     - Suggested fix: apply ACCOUNT_LOCK_TIMEOUT_MS to status changes as well, answer 503 with Retry-After: 1, and add an AC.
