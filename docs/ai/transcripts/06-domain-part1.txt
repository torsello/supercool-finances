     Findings

     1. High: a lost database connection crashes the whole replica instead of failing one request
     - Where: src/platform/db/transaction-runner.ts:55
     - What is wrong: run() takes a client from the pool but never listens for its 'error' event.
       - While a client is checked out, pg-pool removes its own error listener (node_modules/pg-pool/index.js:344).
       - When the connection drops unexpectedly, the client emits 'error' from its end handler (node_modules/pg/lib/client.js:222 → _handleErrorEvent at line 422). This happens even when a query was running and has already been rejected.
       - With no listener, Node throws ERR_UNHANDLED_ERROR and the process exits.
       - So the branch that handles "ROLLBACK failed / unknown state" (plan 000 section 6.1) never gets to run with a real connection. The unit tests only use FakeClient, so they don't catch this.
     - How to trigger: while changeAccountStatus waits on a row lock or sits between statements, run SELECT pg_terminate_backend(<pid>) from another session. The same happens when idle_in_transaction_session_timeout (10 s) fires, on an RDS failover, or when RDS Proxy drops a connection.
     - Impact: every request in flight on that replica is lost, not just one. During a failover all replicas crash at once. This contradicts ADR-0014 ("a burst of 503s"). Money stays correct because Postgres rolls back uncommitted work.

       - Add on/off to RunnerClient.
       - In run(), attach client.on('error', e => { connection.broken ??= e }) right after connect(), and remove it in the finally before release(connection.broken).
