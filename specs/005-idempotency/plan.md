## 2. Data model changes

Migration `idempotency-keys` (05-schema):

```sql
CREATE TABLE idempotency_keys (
  user_id     uuid        NOT NULL,
  key         text        NOT NULL CHECK (char_length(key) BETWEEN 1 AND 255),
  fingerprint char(64)    NOT NULL CHECK (fingerprint ~ '^[0-9a-f]{64}$'),
  status      smallint,
  headers     jsonb,                 -- {"content-type": ..., "location": ...}; never X-Request-Id
  body        bytea,                 -- the exact bytes sent
  created_at  timestamptz NOT NULL,
  expires_at  timestamptz NOT NULL,
  PRIMARY KEY (user_id, key)
);
CREATE INDEX idempotency_keys_expiry ON idempotency_keys (expires_at);
GRANT SELECT, INSERT, UPDATE, DELETE ON idempotency_keys TO scf_app;
```

The completeness check (IDM-R18) is a constraint trigger `AFTER INSERT OR UPDATE ... DEFERRABLE INITIALLY DEFERRED FOR EACH ROW` whose function reads the row again by its primary key at commit, because `NEW` holds the version of the statement that fired it, not the final one. If the row still exists with `status`, `headers` or `body` null, it raises SQLSTATE 23514 with the constraint name `idempotency_keys_complete`. So an insert completed by an update before the commit passes, and an incomplete row never commits (IDM-AC20). The service maps that error to 500, because it means a defect (plan 000 section 6.3). `DELETE` is granted for the cleanup, which runs as the runtime role (DEP-R37).

## 3. The key step

The fingerprint is computed before the database transaction, from the method, the path as received without the query string, and the parsed JSON body in canonical form (IDM-R05). Then, inside one attempt of the transaction runner (plan 000 section 6.1), `idempotent-runner.ts` runs:

| 3   | `INSERT INTO idempotency_keys (user_id, key, fingerprint, created_at, expires_at) VALUES ($user, $key, $fp, now(), now() + $ttl * interval '1 second') ON CONFLICT (user_id, key) DO NOTHING RETURNING true AS claimed`                                                              | A row returned: a first request; the key is claimed. It waits while a first request with the same key, not yet committed, holds the conflicting insert, and then inserts nothing if that request committed, or claims the key if it rolled back (IDM-R10).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |

It waits while a concurrent request holds the row to replace it, and then updates nothing if that request committed its replacement.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| 3c  | Nothing updated: `SELECT fingerprint, status, headers, body, expires_at <= clock_timestamp() AS expired FROM idempotency_keys WHERE user_id = $user AND key = $key`, without a lock                                                                                                  | Same fingerprint: `ROLLBACK`, replay the stored response (IDM-R07). How the operation's outcome ends the transaction (section 1.3 of the spec):

- **201:** step 9 stores the response the presenter built, `Location` included, then `COMMIT`.
- **404 at the lookup, or a business rejection** (409 `already-reversed`, the 422 types of section 1.3 of the spec), including one raised as a 23505 by the unique constraint of REV-R05: `ROLLBACK TO SAVEPOINT work`, step 9 with the problem response, `COMMIT`.
- **422 `validation-error`, a 503 (an account lock timeout, retries exhausted, a statement timeout, or the request timeout before `COMMIT` was sent) or a 500:** `ROLLBACK`, so the key row goes too and a retry runs again (IDM-R16, IDM-R17).
- **Request timeout after `COMMIT` was sent:** the commit finishes after the 503; the outcome is unknown to the client, as for a gateway error, and if the commit succeeded the key row holds the 201, so a retry with the same key gets it by replay (IDM-R17, SEC-R33). A 40P01 or 40001 re-runs the whole attempt from step 1, key insert included.

Steps 3, 3b and 3c share one wait budget: before step 3b and before every pass back to step 3, the runner calls `SELECT app.set_lock_timeout($remaining)` with the whole milliseconds left until the deadline of step 2. When less than 1 ms remains before step 3b, step 3b is skipped and step 3c still reads the row, which takes no lock: a live row is replayed (IDM-R07) or answered 422 (IDM-R09), so a request whose wait ended just as the first request committed still gets its stored response (IDM-R10), and a missing or expired row answers `IdempotencyWaitTimeout` (409 `request-in-progress`, `Retry-After: 1`). When less than 1 ms remains before a pass back to step 3, the runner answers `IdempotencyWaitTimeout` at once. `lock_timeout` bounds each wait, not their sum, so without this an attempt could wait for the key once at step 3 and again at step 3b; with it, one attempt never waits for the key longer than `IDEMPOTENCY_WAIT_TIMEOUT_MS` in total, as SYS-R35 and SEC-R35 count it. A 55P03 at any of these steps is `IdempotencyWaitTimeout` (409, IDM-R12); one at any later step is `AccountLockTimeout` (503, IDM-R13). `kysely-key-store.ts` runs the key-wait steps in the unit of work's key-wait scope, and `sqlstate.ts` tells them apart by the step at which the error was raised (plan 000 section 6.3).

The replay is the stored `status`, `headers` and `body` bytes, plus the current request's `X-Request-Id` and `Idempotent-Replayed: true`. The replay step comes before validation and every later check, and the query string is not part of the fingerprint, so a replay never depends on `MAX_AMOUNT_MINOR`, the accounts' state, the query string or the code version (IDM-R08). The presenter builds every new body, so the `extra-response-member` seam (plan 000 section 8) changes new responses only. Account creation with a key runs the same steps with no lookup or lock (plan 001 section 3.1).

## 4. Cleanup

`npm run idempotency:cleanup` connects with `DATABASE_URL` (the runtime role) and repeats, each batch in its own database transaction:

1. `BEGIN`
2. `SELECT app.set_statement_timeout(600000)` (section 1.9 of spec 007)
3. `WITH doomed AS (SELECT user_id, key FROM idempotency_keys WHERE expires_at <= now() ORDER BY expires_at LIMIT 1000 FOR UPDATE SKIP LOCKED) DELETE FROM idempotency_keys k USING doomed d WHERE k.user_id = d.user_id AND k.key = d.key`
4. `COMMIT`

It stops after a batch that deletes fewer than 1000 rows, prints `{"deleted": n}` with the total on one line, and exits 0; it exits 2 with a fixed message and the SQLSTATE on stderr, never the URL or the driver's message, when it cannot connect or a statement fails (IDM-R22). A row locked by a request in progress is skipped, not waited for.
