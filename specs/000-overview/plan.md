# 000 · Overview · Plan

How the shared platform is built: the request pipeline of SYS-R31, the transaction runner, the movement transaction skeleton that plans 001, 003 and 004 follow, the error model, the test seams and the test infrastructure. It also places every SYS acceptance criterion in a phase and a test file. The spec wins over this plan; where they disagree, the plan is wrong.

## 1. Conventions every plan follows

**Where an AC is proven.** An AC is placed in the first phase in which its When can be performed as written and its whole Then observed at its Level:

- An AC whose When is a request by a user (a deposit, a read, a freeze) or whose Then is an HTTP answer is proven through the HTTP API, from 08-api.
- An AC whose When writes directly to the database, runs a domain function or runs a script is proven in the phase that builds what it exercises: 05-schema for the database checks, 06-domain for the domain, the use cases and the reconciliation.
- An AC whose Given starts the service with a variable of spec 007 (`DB_POOL_ACQUIRE_TIMEOUT_MS`, `REQUEST_TIMEOUT_MS`, `SHUTDOWN_TIMEOUT_MS`) goes to 09-hardening, where the service first reads those variables. An AC that needs `/metrics` goes to 09-hardening too, where the metrics server of spec 007 is built and `@prometheus-io/client` is first used (docs/dependencies.md).
- e2e ACs go to 11-e2e; `ci` ACs go to the phase that adds the CI step their `Verified by` line names.

**How tests are named.** A test names an AC ID only when it proves that whole AC. A test written in an earlier phase for a building block (a constraint, a use case, the retry loop) is named by the requirement IDs it proves, for example `it('MOV-R16 refuses a withdrawal above the balance', ...)`, and is renamed or extended to the AC ID in the phase where the AC becomes whole. `npm run trace` ignores requirement IDs.

**Order of the 05-schema tasks.** The 05-schema tasks of every `specs/*/tasks.md` run in one cross-spec order, because later tasks need the tables and helpers of earlier ones. Each 05-schema task names its step:

1. Roles and functions: the roles and init script, the migration scripts, the scratch-database part of `test/support/db.ts`, `app-functions` and `runtime-role-settings` (plan 000), and the `postgres` healthcheck (plan 008).
2. Accounts: the migration `accounts` (plan 001).
3. Ledger: the migration `ledger` (plan 002), with the reversal link of plan 004.
4. Settlement accounts: the migration `settlement-accounts` (plan 002).
5. Audit: the migration `audit-records` (plan 000).
6. Test helpers: the Kysely instance and `Database` interface, the rest of `test/support/db.ts` with `writeDirectDeposit`, and `test/support/sessions.ts` (plan 000).
7. The database-check ACs and the remaining schema tasks: the ledger ACs of plan 002, the reversal link check of plan 004, the key table of plan 005 and the readiness grant of plan 007.

**Order of the 08-api tasks.** The 08-api tasks of every `specs/*/tasks.md` also run in one cross-spec order, because most ACs need routes of several plans:

1. Authentication and authorization: configuration of `JWT_*`, the verifier, the hooks (plan 006).
2. Error handler and pipeline: configuration, `toProblem`, the shared schemas, `/v1` routes, the composition root and the test app (plan 000).
3. Account routes (plan 001).
4. Idempotency service wiring: the key header, the replay and the runner in the composition root (plan 005).
5. Movement and reversal routes (plans 003 and 004).
6. The ACs that need them: the SYS ACs of plan 000 and the remaining HTTP ACs of every plan, each once the routes it names are served.

**How tasks are ticked.** A task names an AC ID on its line only if the AC is proven once the task is done; building-block tasks name requirement IDs. A task is ticked only in its own phase.

## 3. Data model changes

Plans 001, 002 and 004 own the accounts, ledger and reversal tables; plan 005 owns `idempotency_keys`. This plan owns the roles, the session functions, the runtime role's settings and the audit table.

**Roles** (section 1.3 of spec 002, ADR-0018), created by `docker/postgres/init/01-databases.sql` locally and in CI:

```sql
CREATE ROLE scf_owner LOGIN CREATEDB CREATEROLE PASSWORD 'scf_owner_local_only';
CREATE ROLE scf_app LOGIN PASSWORD 'scf_app_local_only';   -- NOSUPERUSER, NOCREATEDB, NOCREATEROLE by default
GRANT scf_app TO scf_owner WITH ADMIN TRUE, INHERIT FALSE, SET FALSE;  -- lets the owner ALTER ROLE scf_app SET
CREATE DATABASE supercool_dev OWNER scf_owner;
CREATE DATABASE supercool_test OWNER scf_owner;
```

`CREATEDB` lets tests create the scratch databases some ACs ask for (LED-AC06, LED-AC16). `.env.example` gets `MIGRATION_DATABASE_URL` and `TEST_MIGRATION_DATABASE_URL` (owner role) and points `DATABASE_URL` and `TEST_DATABASE_URL` at `scf_app`; `npm run env:sync` adds the new variables, and the owner updates the two existing URLs in `.env` by hand, since env:sync never rewrites a value.

**Migration `app-functions`** (SEC-R31, section 1.9 of spec 007):

```sql
CREATE SCHEMA app;
CREATE FUNCTION app.set_lock_timeout(ms integer) RETURNS void LANGUAGE plpgsql SECURITY INVOKER AS $$
BEGIN
  IF ms IS NULL OR ms < 1 OR ms > 60000 THEN RAISE EXCEPTION 'lock timeout out of range' USING ERRCODE = '22023'; END IF;
  PERFORM set_config('lock_timeout', ms || 'ms', true);
END $$;
CREATE FUNCTION app.set_statement_timeout(ms integer) ...  -- same shape, 1 to 3600000; the reconcile and cleanup scripts call it with 600000 (section 1.9 of spec 007)
REVOKE ALL ON FUNCTION app.set_lock_timeout(integer), app.set_statement_timeout(integer) FROM PUBLIC;
REVOKE EXECUTE ON FUNCTION app.set_lock_timeout(integer), app.set_statement_timeout(integer) FROM scf_owner;  -- the owner's implicit EXECUTE too
GRANT USAGE ON SCHEMA app TO scf_app;
GRANT EXECUTE ON FUNCTION app.set_lock_timeout(integer), app.set_statement_timeout(integer) TO scf_app;
```

After the migration, `scf_app` is the only role that holds `EXECUTE` on either function, as SEC-R31, SEC-R48 and ADR-0018 say; a superuser can still call them, as it can do anything.

**Migration `runtime-role-settings`** (SEC-R29): through dynamic SQL, `EXECUTE format('ALTER ROLE scf_app IN DATABASE %I SET statement_timeout = %L', current_database(), '5s')` and the same for `idle_in_transaction_session_timeout = '10s'`; the down migration runs `ALTER ROLE scf_app IN DATABASE %I RESET ...` for both. Each database thus records and reverts its own settings, as node-pg-migrate records the migration per database, and rolling back one database never changes another.

## 6. Database transactions

### 6.1 Transaction runner

`runTransaction(work, { retry })`: it takes one pool connection, keeps it for every attempt and releases it after the last one, so the pool acquire timeout is waited at most once per request, as SYS-R35 and SEC-R35 count it. Each attempt runs `BEGIN ISOLATION LEVEL READ COMMITTED`, runs `work`, and `COMMIT`. On any error it runs `ROLLBACK`. With `retry: 'movement'`, an error with SQLSTATE 40P01 or 40001 (at any statement, `COMMIT` included) starts a new attempt after `sleep(random() × bound(n))`, `bound(n) = min(200, 10 × 2^(n−1))` ms, up to 3 attempts; after the third it throws `RetriesExhausted` (SYS-R18, SYS-R19). No other error is retried: 55P03 and 57014 are answered at once (MOV-R20, SEC-R32). Movements and reversals use `retry: 'movement'`; account creation and status changes use `retry: 'none'`, since SYS-R18 covers money movements only. Reads run single statements outside an explicit transaction. If `ROLLBACK` fails, or the connection is in any state the runner cannot account for (a transaction possibly still open or aborted, a protocol error), the runner releases the client with an error (`release(err)`), so the pool destroys it instead of handing it to another request.

### 6.3 Error classification

| 57014                                                      | any                                     | `StatementTimeout` (plan 007)                                                   | no      |

| anything else                                              | any                                     | rethrown, answered 500                                                          | no      |

## 7. Error mapping

`toProblem` in `src/platform/http/error-handler.ts` is the only place that turns an error into a status. Every body is `application/problem+json` with `type`, `title`, `status`, `detail` and `requestId`, and `errors` for validation; `title` and `detail` are fixed per type, so bodies of one type differ only in `requestId` (SYS-R05, MOV-R15). The not-found body is one body for every resource, account, transaction or route, so SYS-AC25 and MOV-AC18 can compare them.

## 9. Test infrastructure

- **One shared test database.** Integration tests run against `TEST_DATABASE_URL` as `scf_app`, one file at a time (`fileParallelism: false`). A Vitest `globalSetup` (`test/integration/global-setup.ts`, 05-schema) migrates it to the latest migration as `scf_owner`. Each test creates fresh user ids and accounts, leaves committed data reconciled, every transaction balanced and every cached balance equal to the sum of its entries, as the reconciliation run by CI after the integration tests checks (LED-R22), and asserts a settlement balance only as a change (section 1.5 of spec 002). A test that needs drift creates it in a transaction it rolls back, or in a scratch database.
- **Scratch databases.** `test/support/db.ts` creates a database as `scf_owner`, migrates it with node-pg-migrate's programmatic runner, and drops it after the test.
- **Direct writes.** `test/support/db.ts` holds a runtime-role connection for "written directly to the database", and the helper `writeDirectDeposit(account, amount)` of the preamble of section 3 of spec 002: as the runtime role, in one database transaction, it writes a complete deposit as the service would, with the transaction row, both entries, the cached balance change and an audit record of action `deposit` by a test operator, so the shared test database still reconciles (LED-R22). The ACs of plan 002 placed in 05-schema and 06-domain set up their balances with it.
- **Sessions that hold locks.** `test/support/sessions.ts` opens a separate session as `scf_owner`, through `TEST_MIGRATION_DATABASE_URL`, so the runtime role's `idle_in_transaction_session_timeout` of 10 s never ends a lock a slow test still needs, and so it may take the `ACCESS EXCLUSIVE` table lock of SEC-AC24. It takes `SELECT ... FOR UPDATE` (or `FOR NO KEY UPDATE`) on a row, and waits until a given backend is blocked by it, read with `pg_blocking_pids` only, so tests never sleep a fixed time. The owner role cannot read the runtime role's `wait_event_type` in `pg_stat_activity`, which only the same role or a member of `pg_read_all_stats` may see.
- **Apps.** `test/support/app.ts` builds the production app or the test app with configuration overrides, captures log lines through the logger's destination stream, and sends requests with `inject`, or over TCP when an AC says the app listens. Several apps against one database stand for replicas.
- **SQL capture.** `test/support/sql-capture.ts` (09-hardening, plan 007) wraps `pg`'s client `query` inside the test process to record the statements of a connection in order. It is test wiring around the driver, not one of the five app seams. Until it exists, the statement-order tests of 07-idempotency (plans 003 and 004) capture through the unit of work's connection, which they build themselves.
- **Rate limit in tests.** From 09-hardening, `test/support/app.ts` builds every app with `RATE_LIMIT_USER_MAX` "1000000", except where an AC names its own value (section 1.6 of spec 007).
- **Tokens and requests.** `test/support/tokens.ts` mints tokens with the test `JWT_SECRET` (plan 006); `test/support/http.ts` has helpers such as `deposit(o1, a1, "100")` that add a fresh `Idempotency-Key`.
