## 2. Data model changes

Only the grant of the migration `readiness-grant`. The settings `statement_timeout` 5 s and `idle_in_transaction_session_timeout` 10 s on `scf_app`, and the functions `app.set_lock_timeout(ms integer)` (1 to 60000) and `app.set_statement_timeout(ms integer)` (1 to 3600000, called with 600000 by the reconcile and cleanup scripts), are the migrations `runtime-role-settings` and `app-functions` of plan 000 section 3.

## 3. Placement in the request pipeline

Following section 1.3, inside a replica: route, authentication (`onRequest`, plan 006), **per-user rate limit** (`onRequest`, this plan), role (`onRequest`, plan 006), **media type** and **body size** (the content-type parser and `bodyLimit`, which run when Fastify reads the body, after every `onRequest` hook), malformed request, then the idempotency step. None of these answers is stored for replay. A request without a valid token never reaches the rate limit, because authentication answers 401 first.

- **Per-user limit.** A Redis counter per user created with a TTL of `RATE_LIMIT_USER_WINDOW_S` and incremented atomically by the store's script, one round trip. Above `RATE_LIMIT_USER_MAX` the hook answers 429 with `Retry-After` = the counter's remaining TTL rounded up, at least 1. A Redis error or a command timeout lets the request through: the hook catches the store's error itself, not through the plugin's `skipOnError`, which would swallow it, so that it can add 1 to `scf_rate_limit_store_errors_total` and log `warn` once on the transition to unavailable and `info` once on recovery.
- **Bodies.** A body without a matching `Content-Type` is 415 before any byte is parsed; above 16384 bytes, by `Content-Length` or by the bytes received, 413. A request without a body needs no `Content-Type` (a freeze, SEC-AC08).

## 4. Timeouts, connections and shutdown

| Layer                  | Where it is enforced                                                         | Answer                                                         |
| ---------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------- |
| Account lock, key wait | `app.set_lock_timeout` per transaction (plans 000, 003, 005)                 | 503 or 409, SQLSTATE 55P03                                     |
| Statement              | `statement_timeout` 5 s on `scf_app`                                         | 503, SQLSTATE 57014, not retried (SEC-R32)                     |
| Pool acquire           | `connectionTimeoutMillis` of the `pg` pool                                   | 503, counted in `scf_db_pool_acquire_timeouts_total` (SEC-R37) |
| Redis command          | `commandTimeout` of `ioredis`                                                | the request goes on, as under the limit                        |
| Request                | `request-timeout.ts`: a timer from the moment the request is received        | 503 (SEC-R33)                                                  |
| Keep-alive             | `keepAliveTimeout` 65 s on the Node server, above nginx's 60 s and the ALB's | (SEC-R34)                                                      |

The configuration loader refuses to start when `REQUEST_TIMEOUT_MS` is not greater than `DB_POOL_ACQUIRE_TIMEOUT_MS` + `REDIS_COMMAND_TIMEOUT_MS` + 3 × (`IDEMPOTENCY_WAIT_TIMEOUT_MS` + 2 × `ACCOUNT_LOCK_TIMEOUT_MS`) + 30, or when `SHUTDOWN_TIMEOUT_MS` is less than `REQUEST_TIMEOUT_MS`, naming the variables involved (SEC-R35).

At `REQUEST_TIMEOUT_MS` the service answers 503 at once and rolls back afterwards, as SEC-R33 says. The design is recorded in [ADR-0022](../../docs/adr/0022-request-timeout-answer-first-then-roll-back.md):

- **Answer first.** At the deadline the runner marks the request timed out and answers 503 `/problems/service-unavailable` with `Retry-After: 1`. Nothing it does afterwards changes that answer.
- **No further statement.** The runner sends no statement for the request after the deadline other than its `ROLLBACK`; a unit of work that asks for the next statement gets the timeout error instead.
- **Roll back after the statement in flight.** The runner awaits the statement in flight, whatever its outcome, then sends `ROLLBACK` and releases the connection. `statement_timeout` ends that statement on the server within 5 s; the runner also keeps a client-side limit a little above it, `statement_timeout` + 1000 ms, for a reply that never comes (for example a network cut between the replica and the database): when that limit fires, it releases the client with an error, so the pool destroys it. If `ROLLBACK` fails, or the connection state is unknown, the client is released with an error and destroyed too (plan 000 section 6.1). With no transaction open (the request is waiting for a pool connection, or between transactions), there is nothing to roll back.
- **`COMMIT` in flight.** A commit already sent finishes: the runner awaits it and releases the connection, and the answer stays 503. The outcome is unknown to the client, as for the load balancer's gateway errors (DEP-R16), and a retry with the same `Idempotency-Key` gets the stored response (SEC-R33, SEC-AC38).
- **No cancel.** The service never cancels a statement from another connection: a cancel by backend pid can reach another request's statement behind RDS Proxy, or after the pid is reused, while `statement_timeout` already bounds every statement to 5 s.

Shutdown, on SIGTERM or SIGINT, and on those signals only (SEC-R25): readiness answers 503 at once; after `SHUTDOWN_DRAIN_DELAY_MS` the server stops accepting connections and logs that it did; idle keep-alive connections close; requests in flight, counting the clean-up of every request already answered 503 at its request timeout (its statement in flight, then its rollback or the commit already sent), run to completion within `SHUTDOWN_TIMEOUT_MS`; then the pool, the readiness connection and Redis close in that order and the process exits 0. At the deadline the coordinator destroys the remaining connections, those of unfinished clean-ups included, which rolls back their transactions, closes the same three in the same order and exits 1 (section 1.8 of the spec).

Signals and uncaught errors, decided by the owner on 2026-10-08: `src/main.ts` listens for SIGTERM and SIGINT itself. A further signal while the shutdown runs is logged at `warn` and otherwise ignored, so a second Ctrl-C never cuts the ordered close short; the shutdown's own deadline, `SHUTDOWN_DRAIN_DELAY_MS` + `SHUTDOWN_TIMEOUT_MS` plus a margin of 5 s for closing the resources, still bounds the exit. Other signals do not start the shutdown. An uncaught exception or unhandled rejection runs the same ordered shutdown through `close-with-grace`, which is set to skip every signal because it exits at once on a second one, and the process then exits 1.

| ---------------------- | ----------------------------------------------------------------------------- | ------ | ---------------------------------- | ----------------------------- | ----------------------------- |

| `UnsupportedMediaType` | a body with a missing or other `Content-Type`                                 | 415    | `/problems/unsupported-media-type` |                               | no                            |

## 8. Decision recorded

SEC-AC26, SEC-AC29, SEC-AC33 and SEC-AC36, and DEP-AC05 and DEP-AC12 of plan 008, are unit tests that read `compose.yaml` with the `yaml` package (eemeli/yaml), a development dependency approved by the owner on 2026-10-08 and recorded in `docs/dependencies.md`, first used in 10-runtime. The alternatives, running `docker compose config` from unit tests or parsing the file line by line, were rejected: the first makes `npm run check` need Docker, and the second is fragile.
